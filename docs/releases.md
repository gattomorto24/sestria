# Pubblicare una versione di Sestria

Il repository ufficiale è [gattomorto24/sestria](https://github.com/gattomorto24/sestria).

1. Aumenta **version/code** e **version/name** nel preset release `mobile/export_presets.cfg`. Aggiorna anche la versione di fallback in `mobile/scripts/updater.gd` e `mobile/native/SestriaUpdates.java`. Per i computer aggiorna `config/version` in `project.godot`, le versioni dei preset macOS e Windows in `export_presets.cfg` e `FALLBACK_VERSION` in `scripts/desktop_updater.gd`.
2. Compila e verifica l’APK con la stessa chiave release. Il nome deve essere `Sestria-vVERSIONE-Android.apk`, ad esempio `Sestria-v4.4-Android.apk`.
3. Esporta Mac (`Sestria-vVERSIONE-macOS-universal.zip`, app universale con firma ad hoc) e Windows (`Sestria-vVERSIONE-Windows-x64.zip`). Genera `SHA256SUMS.txt` con i tre pacchetti.
4. Salva i sorgenti nel repository e crea una release GitHub con tag `vVERSIONE`, ad esempio `v4.4`. Non usare una prerelease per l’aggiornamento stabile.
5. Allega i tre pacchetti, `SHA256SUMS.txt` e le note della versione e pubblica la release. GitHub calcola il digest SHA-256 di ogni asset; le app lo leggono dall’API delle release. Android sceglie l’APK, Mac e Windows il proprio archivio.
6. **Edizione web (passo fisso a ogni release).** Con la versione già aggiornata in `project.godot`, esegui `tools/export_web.sh VERSIONE --publish`. Lo script esporta in `build/web` (Godot 4.7.1, template web single-thread, renderer Compatibility) e sostituisce il branch `gh-pages` con un unico commit che contiene solo la build web; GitHub Pages la serve su https://gattomorto24.github.io/sestria/. Non servono Actions. Senza `--publish` esporta soltanto, per provarla con `python3 tools/web/serve.py build/web`. Controlla che la pagina carichi e che `version.json` riporti la versione appena pubblicata; vedi la sezione «Edizione web» più sotto.
7. **Pacchetti contenuti (passo fisso a ogni release).** Prima di pubblicare, con `content.json` e `mobile/content.json` aggiornati alla versione (`"content"`), esegui `tools/export_content_pack.sh VERSIONE`. Lo script esporta `Sestria-vVERSIONE-macos-content.pck`, `…-windows-content.pck` e `…-android-content.pck`, crea il manifest `Sestria-vVERSIONE-content.json`, lo firma con la chiave privata di firma contenuti e lo ricontrolla con lo stesso codice (e la stessa chiave pubblica) che stanno nell’app. **Allega alla release anche questi quattro file** (`gh release upload vVERSIONE build/release/Sestria-vVERSIONE-*content*`). Il pacchetto completo (passi 2–3) va comunque sempre pubblicato.
8. Dalla versione precedente apri **Opzioni → Aggiornamenti**: premi Verifica, poi **Aggiorna**, poi **Riavvia per applicare**. Sul Mac, in Windows e su Android l’app deve riavviarsi da sola, mostrare la nuova versione e non riproporre l’aggiornamento. Se la release non ha pacchetto contenuti compatibile, l’app deve invece proporre il pacchetto completo spiegando il motivo.

Non servono server, token dentro l’app o cambiamenti al codice per ogni release (il manifest dei contenuti è un asset della release stessa). La relazione fra nome della versione e versionCode deve restare crescente. Un APK firmato con un’altra chiave, di un’altra app, incompleto o precedente viene rifiutato.

La chiave e la password restano nella cartella privata di firma, esclusa da Git. Conservane una copia privata: senza la stessa chiave non è possibile aggiornare le copie già installate.

## Aggiornamenti dall’app: pacchetti contenuti

Mac, Windows e Android si aggiornano dall’app senza scaricare né installare nulla a mano, **quando la release cambia solo i contenuti**: script GDScript, scene, asset e shader. Il percorso è: Verifica → Aggiorna (barra di avanzamento) → Riavvia per applicare.

**Come funziona.** Ogni release allega un pacchetto di risorse Godot (`.pck`) per piattaforma e un manifest firmato. L’app scarica il manifest e il pacchetto da GitHub (HTTPS, dimensione massima 150 MB, scrittura su `.part` e rinomina atomica in `user://updates/content/`), controlla firma del manifest, SHA-256, dimensione, digest di GitHub e versione del motore nell’intestazione del `.pck`, e registra l’aggiornamento. Al riavvio `boot.gd` (scena principale, senza interfaccia sul desktop) monta il pacchetto con `ProjectSettings.load_resource_pack(…, true)` **prima** di caricare il gioco, così i file del pacchetto sostituiscono quelli integrati. `content.json` dichiara la versione dei contenuti (mostrata in Opzioni); `project.godot` e il codice nativo restano quelli del pacchetto completo installato (la «base»).

**Cosa NON può cambiare.** Il motore Godot, il codice nativo (Java su Android: `native/*.java`, il manifest, i permessi, le librerie) e `project.godot`. Quando una release ne ha bisogno bisogna alzare `"min_base"` in `content.json` / `mobile/content.json` alla versione della release: le app con una base più vecchia non offrono il pacchetto contenuti ma propongono il pacchetto completo (Download su desktop, APK su Android) e spiegano il motivo. Lo stesso vale se manca il manifest o il pacchetto della piattaforma, se la firma non è valida, se il motore è diverso o se su quel dispositivo la stessa versione era già stata respinta. Regola pratica: se hai toccato `native/`, `addons/`, `project.godot`, `export_presets.cfg` o aggiornato Godot, `min_base` = nuova versione.

**Sicurezza (carica codice scaricato).** Il pacchetto contiene script GDScript che l’app eseguirà, quindi vale quanto un eseguibile. Difese: (1) solo HTTPS da `github.com` del repository ufficiale, URL controllato per prefisso; (2) il manifest è firmato RSA-3072 / SHA-256 con una chiave privata che sta fuori da Git e fuori da GitHub (`build/content-signing/`, `SESTRIA_CONTENT_KEY`); la chiave pubblica è incorporata in `scripts/content_pack.gd`. Chi riuscisse a pubblicare una release (account GitHub compromesso) **non** può quindi far eseguire codice alle app già installate senza la chiave di firma; (3) il manifest contiene nome, dimensione e SHA-256 del pacchetto, e GitHub ne calcola un digest indipendente che deve coincidere; (4) il manifest lega pacchetto, versione e motore: un manifest vecchio non può sostituire uno nuovo (la versione deve essere più recente di quella integrata) e un pacchetto non può essere scambiato; (5) i pacchetti vivono in `user://` (non toccano il bundle firmato dell’app né richiedono permessi); (6) il codice che verifica (`boot.gd`, `content_pack.gd`, chiave pubblica) è già caricato prima del montaggio, quindi un pacchetto non può disattivare il controllo del proprio avvio; per cambiarli serve un pacchetto completo. Limiti dichiarati: chi ha già accesso in scrittura ai dati dell’app sul dispositivo può sostituire i file (ma allora può già fare molto altro); la chiave di firma va custodita come la chiave Android (se si perde, le app esistenti accettano nuovi pacchetti solo da una nuova release completa con la nuova chiave pubblica); i pacchetti Mac e Windows non sono notarizzati come l’app e la firma ad hoc del bundle non copre `user://`.

**Avvio sicuro e rollback.** Pacchetto assente, troncato, corrotto (SHA-256 diversa), per un altro motore, non più nuovo rispetto all’app o che richiede una base più recente: viene cancellato e si usano i file integrati, senza bloccare l’avvio. Dopo il montaggio `boot.gd` carica tutti gli script e le scene (`Content.validate_loaded`): se uno non si compila o la scena non parte, il pacchetto viene respinto (la versione è ricordata e non verrà riproposta come contenuto su quel dispositivo) e l’app si riavvia da sola con i file integrati. L’avvio è «confermato» due fotogrammi dopo che il gioco è partito; se l’app si chiude prima della conferma, il tentativo successivo ripristina i file integrati. Un errore di esecuzione dopo l’avvio (non di caricamento) non viene rilevato: provare ogni pacchetto prima di pubblicarlo.

**Riavvio.** Desktop: Windows riavvia l’eseguibile; macOS apre un’altra istanza del bundle con `open -n Sestria.app`, risalendo dal percorso dell’eseguibile, e poi chiude la vecchia. Android: `SestriaUpdates.restartApp()` avvia `SestriaRestartActivity` in un processo separato (`:restart`), che uccide il processo principale e rilancia l’app (rilanciare dallo stesso processo fa perdere la nuova attività). Se il riavvio non riesce, l’app chiede di riaprirla a mano.

**Prima volta.** Le copie già installate della 4.5 non hanno questo meccanismo: la prima release con i pacchetti contenuti va installata ancora a mano (pacchetto completo), e in quella release `min_base` deve essere la versione della release stessa (le app precedenti non hanno il codice per usare un pacchetto). Dalla successiva basta Aggiorna.

**Test.** `tests/content_pack_test.gd` e `mobile/tests/content_pack_test.gd` (firma, compatibilità, installazione atomica, file corrotto/troncato/assente, rollback, montaggio reale di un `.pck` di prova); `tests/desktop_updater_test.gd` e `mobile/tests/updater_test.gd` (scelta contenuti/pacchetto completo, ripiego e motivi); `tests/content_release_check.gd` (controllo finale dei file della release, lanciato da `export_content_pack.sh`). Prova di punta a punta senza pubblicare nulla: `tools/content/fake_release_server.py CARTELLA v4.6 PORTA` imita le API delle release e `SESTRIA_UPDATE_API` / `SESTRIA_UPDATE_RELEASES` le puntano al server (solo build di sviluppo); `godot --headless --script res://tests/content_update_e2e.gd` scarica e installa, poi si avvia l’app esportata con lo stesso `HOME`. Su Android: preset **Android Content Smoke** (`mobile/tests/content_android.gd`), da installare sull’emulatore con il server su `10.0.2.2:55192`.

**Verifica reale contro la release pubblicata** (da fare dopo il caricamento degli asset): con una `HOME` di prova, `godot --headless --script res://tests/content_update_e2e.gd -- --pretend=VERSIONE_PRECEDENTE` (senza variabili d’ambiente) deve riportare «available · content», scaricare, verificare e installare il pacchetto vero; poi l’app esportata o `… -- --mount --expect-current` deve mostrare i contenuti nuovi e non riproporre l’aggiornamento.

## Edizione web

La versione web ha la stessa base del progetto desktop (`project.godot`, `scripts/`, `scenes/`, `assets/`) e usa il preset **Web** di `export_presets.cfg`. Funziona solo con il renderer Compatibility (WebGL2) e senza thread, perché GitHub Pages non può inviare gli header COOP/COEP. I template web 4.7.1 (`web_nothreads_release.zip`) si trovano in `~/Library/Application Support/Godot/export_templates/4.7.1.stable`; lo script li copia accanto al binario di Godot se mancano. Sul web non esistono LAN TCP/UDP, aggiornatore e pulsante Esci: `scripts/platform.gd` decide cosa mostrare, ed è il punto dove la sessione online WebRTC dichiarerà `online_available()`. I salvataggi di `user://` vanno in IndexedDB del browser. La pagina si aggiorna da sola: dopo la pubblicazione il browser scarica i file nuovi (la cache di Pages dura fino a circa 10 minuti).

## Verifica reale del download

Per provare ricerca, download e SHA-256 contro l’ultima release pubblica, dalla directory `mobile` esegui:

```sh
godot --headless --script res://tests/updater_live_test.gd
```

Il test scarica l’APK su disco e lo rimuove al termine; non sovrascrive un aggiornamento locale già presente. La verifica della firma è coperta separatamente dal collaudo nativo Android in `mobile/tests/native/`. I test non sono inclusi nell’APK release.

Le nuove release possono essere caricate manualmente da GitHub: GitHub Actions non è richiesto per gli aggiornamenti sui telefoni. Il workflow di verifica nel repository è facoltativo e si avvia manualmente.

## Partite online

Prima di ogni release eseguire `tools/run_online_test.sh` (elenco, invito, partita completa su WebRTC e dati ostili) e, per le app native, controllare che le librerie di `addons/webrtc_native` e `mobile/addons/webrtc_native` siano presenti: senza l’estensione la modalità online sparisce dai menu. Su Windows la DLL `libwebrtc_native…dll` viaggia accanto a `Sestria.exe` (lo script `tools/export_desktop.sh` la include). Su Android la release include le librerie arm64-v8a; i telefoni a 32 bit non vedono la modalità online.
